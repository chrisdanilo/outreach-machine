# Outreach Rulebook

Every rule applies to every machine unless it is listed under "Machine settings". A machine never overrides this file. Changes come only from Chris; questions for Chris go only to the rulings list and appear in the morning report.

**This file is the only place a rule lives (Chris 2026-11-10).** Every other page — the Charter, the phase pages, the customer-type (ICP) files, the helper instructions, the program comments — points here by section number and never restates a rule. A rule found anywhere else is a defect: remove it there and fix it here.

## A · Vocabulary
| Term | Meaning |
|---|---|
| ICP | One type of organization, defined by what it does (function test). Template: Ops/Templates/ICP-TEMPLATE.md |
| Market | One or more ICPs that value the same Message the same way, plus any condition |
| Cluster | Market × Message × Method. Named by launch quarter (CL-Q2-26); unlaunched ideas CL-WIP-### |
| Method | A Thought Leaders delivery mode only: Speaker, Author, Trainer, Mentor, Facilitator, Coach |

| Business day | Monday–Friday that is not a US bank holiday (Federal Reserve list) |

## B · Ground truth
1. Gmail is the record of what was sent and when. If the master list disagrees with Gmail, Gmail wins and the list is corrected.
2. HubSpot is a mirror only. It never decides anything.
3. Questions for Chris go only to the rulings list and show in the morning report.
4. One org, many email domains (Chris 2026-11-10, ENG-R012). Many orgs send mail from more than one domain (a website domain plus a mail domain; school districts, education service districts and county education offices often also use name.k12.<state>.us). All of an org's domains are recorded together as ONE org in the master list's same-org domain list, and every check (sent before C2, do-not-contact C3, existing client C4, own-domain address tests H1/H7, reply matching) reads the whole set. A second domain is recorded only with proof, never on a similar name: (a) the org's own live pages print addresses on it; (b) the org's own auto-reply or reply comes from it; (c) the other domain forwards (redirects) to the org's website; or (d) Apollo's company record lists it. How second domains are found (the old Machine 1 step E1.8, restored): for every org it researches, the find-people step records BOTH the website domain (where the site lands after any redirect) and the mail domain (the domain of the addresses it actually read off the org's own pages) — even when they are the same. If they differ, the pair is a CANDIDATE and is checked in Apollo the same night (patch 2's check) before anything is joined — association pages often print volunteers' day-job addresses, so an address on the page is not proof by itself (replay 2026-11-10). An org whose domain set is only partly on record (an address on its page uses a domain that belongs to another org with a thread, a client or a do-not-contact entry) is held, not cleared, until Apollo says the two are not the same org. No domain is ever guessed. Patch 1: every domain an existing client's or excluded org's own contacts use counts as that org's domain in the client and do-not-contact checks (C3/C4), so a client writing from a second domain is still caught. Patch 2: when a domain the machine has not seen turns up in real data for an org (its Gmail replies or auto-replies, an Apollo-found address), it is checked in Apollo: if Apollo's people search returns the same organization for that domain and the org's known domain, the pair is recorded; otherwise it is recorded as not the same and never joined. Every pair carries its proof and is kept in one same-org domain list. Mail domains shared by many unrelated orgs (state agencies, universities hosting several programs, consumer mail) are never joined.
5. One person on two records (Chris 2026-11-10, Issue 3). Two master-list records that list the same person's address are one org when they carry the same name or the org's own acronym and do not both already have a live email thread: they are folded into one record automatically and the fold is logged. Any other pair (different names — e.g. a board member or partner who sits on two orgs — or two live threads) is held: neither gets an Email 1, and the morning dossier asks "Same person on two orgs?" until Chris rules same org (merged) or keep both.

## C · Safety — never broken
1. Email 1 is never sent by a machine. It is a draft; Chris adds the GIF and sends it.
2. Each org is contacted once: one thread per org (or per event-owning team inside an org). Sent mail is checked before any draft.
3. Do-not-contact is absolute (unsubscribes, "don't contact me" replies, the do-not-contact list). A register row is org-wide (scope domain) unless Chris rules it person-only (scope person: only the named addresses are blocked — Trying Together, 2026-11-03).
4. Existing clients are excluded, checked by the org domain AND every recipient domain. Any prior relationship = hold (CAPA 2026-10-27).
5. Colorado is excluded (Chris works it personally).
6. Copy is frozen: only the greeting and org name vary; templates change only by Chris.
7. Links are never Google-wrapped; drafts are written through Zapier (CAPA 2026-08-26).
8. Every send needs a fresh thread check under 3 minutes old; one send per thread, never retried (CAPA 2026-10-06).
9. Bounce breaker: bounces above 3% stop all sending until Chris rules.
10. When something does not add up: stop and hold, never guess.

## D · Discovery
1. One discovery engine serves every machine, driven by the active ICPs and the source list.
2. It follows finds outward: keynoters → their events; sponsor, parent, partner and child orgs → their speakers and events.
3. Every find goes on the master list tagged with every ICP it fits. Nothing is thrown away: not-fit orgs stay with the reason, so they are never researched twice.
4. No search is repeated (search log).
5. Sources and warm referrers are never emailed; referrers appear in the morning report only.
6. Order of sources for conferences (Chris 2026-11-10, Issue 1): OM-2 searching works umbrella list pages (NAEYC affiliates, NHSA state associations, NAFCC affiliates, the infant mental health alliance) and association directories first, then event calendars, keynoters, partner pages and branch events. A list page drawn by JavaScript is read in the built-in browser, never marked "not found" from a plain fetch.
7. Head Start grantees with no website on file (Chris 2026-11-10, Issue 7): before qualifying, Apollo's free organization lookup (name + state) suggests a website; a suggestion is kept only when Apollo's company name matches the grantee's name closely, and it is a hint until a helper reads that site and a captured page names the org. Apollo credits may be spent on this lookup if it ever stops being free.

## E · Qualify and route
1. An org qualifies when it passes its ICP's fit criteria and has no exclusion from section C.
2. Doubtful fit is never drafted (Chris 2026-11-10; replaces "draft and flag", 2026-10-09). The org is listed in the dossier's top 10 decisions with the reason it is doubtful, and Chris answers yes or no. Yes → it becomes a fit and is drafted on the next night by default. No → not a fit, closed. Until he answers it waits; nothing about it reaches Gmail. People may still be found for it so an approved org is ready the next night.
3. Routing (Chris 2026-11-09, amended 2026-11-10). An org belongs to OM-2 only when it runs a conference that counts; everything else in the market → OM-1. Nothing else decides it. A conference counts when BOTH are true:
   - **It is a conference** — an event type that needs a keynote speaker (conference, convention, summit, symposium, institute, forum, annual meeting; a virtual one counts). A training day, staff training, pre-service or in-service, training or PD series, course or webinar is NOT a conference → OM-1. A type that is not clearly either (retreat, grantee/admin/outcomes meeting, gathering, expo) goes on the "needs Chris's decision" pile: it is not OM-2 until Chris says so, it is asked in the dossier's top 10 decisions ("Is this a conference?"), and his answers build the pattern for these outliers over time (Chris 2026-11-10).
   - **There is a sign it happens in the coming year** — a set date for the next edition; or the newest edition on record is last year's or later (assume it happens again); or two or more past editions on record at about the same time of year; or the event is biennial and its newest edition is within two years. A conference with no date anywhere still counts (F1). One edition from several years ago and nothing else, or not enough on the site to tell → does not count → OM-1.
   The machine reads the org's WHOLE calendar, not the first event it finds, and records every upcoming event (section F6). An org already emailed stays with the machine that emailed it (E6). An org that fits only a conference-only customer type and has no conference that counts belongs to neither machine: it is asked in the dossier's top 10 decisions, and an approved one is drafted the next night. *(Until 2026-11-09 this read "with an outside-keynote path (breakout-only events are out)" — a Claude-built rule, never ruled by Chris. Retired. Until 2026-11-10 any event ever recorded, of any type and any age, counted.)*
4. Event gate (OM-2, Chris 2026-11-09): there is none beyond "a conference exists". Every conference is assumed to have a keynote slot, listed or not — "presenter", "breakout session" and "session proposal" are not keynotes and never rule an event in or out. The offer is a PAID KEYNOTE only, never a free breakout. Whether a keynote is already chosen changes WHEN we approach (section F), never whether.
5. A request for proposals (RFP) or open call needs no special machine: it means the org is ready to hear from us, so outreach opens now (Chris 2026-10-30).
6. When both machines have threads with one org, follow-ups belong only to the owning machine; the other machine's thread stops (Chris 2026-10-30).
7. No conference → hand off to OM-1 (Chris 2026-11-03). OM-2 exists only for orgs that run a conference. A reply or a page saying the org has no conference ends the OM-2 sequence (thread stopped) and moves the org to OM-1 through a `handoff` override that names the prior threads; The org is never restarted at Email 1 once it has heard from us and answered (Chris 2026-11-03): a cold "we haven't met" email after their reply is false and damages trust. Ownership and records move to OM-1; any next touch is Chris's own reply on the existing thread. A new OM-1 Email 1 is drafted only when the org never replied AND Chris sets email1: true on the handoff. Anyone who asked to be removed stays blocked (C3).

## F · Timing (OM-2 events) — Chris's decision tree, 2026-11-09, amended 2026-11-10
1. Planning date = the set date of the next edition; if none, the last edition's date rolled forward (12 months; 24 if biennial) as the interim estimate. **A conference with no date anywhere → approach now** (no known time constraint).
2. Lead: **more than 9 months out → queue, approach 9 months before. 3–9 months out → approach now.** One rule for every event; size is recorded but decides nothing.
3. **A live call for speakers / RFP / open speaker-submission form / keynote request supersedes every timing rule in this section, the under-1-month rule included** (Chris 2026-11-09, confirmed 2026-11-10): if they are asking, we approach now, or on the day the call opens if it states one.
4. **Inside 3 months (Chris 2026-11-10):**
   - **1–3 months out:** no keynote speaker listed → approach now. Keynote speaker listed (or this edition's call has closed) → no outreach for this edition. If the pages read do not show either way → approach now.
   - **Under 1 month out:** no outreach at all for this edition — unless F3 applies (an open speaker form).
5. **An edition we do not approach goes back in the queue and is re-evaluated at the 9-month mark for the next edition** — 9 months before next year's date, which is 3 months after this one (15 months after for a biennial event). This replaces the old "2 months after the event" wait everywhere (Chris 2026-11-10). Nothing is thrown away: every event stays on the master list with its dates, so each year's work makes the next year's easier.
6. Several conferences at one org = a high-value org. Every event gets its own window. The machine looks at the whole calendar and pitches the most relevant event in the good timing range — 3–9 months out first, then 1–3 months, then no date — never simply the soonest (Chris 2026-11-10; e.g. an org with one conference this week and others in February and April is approached about February). The dossier shows every event's URL and one sentence on why that one.
7. Dates are re-checked on every rebuild, so queued events open on their own. The same rule applies to every audience; no audience-specific calendars.
*(Retired: 6 months / 9 months by attendance and the quiet window inside 3 months — 2026-11-09. "Inside 3 months, nothing listed → approach, however close" and "wait 2 months after the event" — 2026-11-10.)*

## G · Who to email
1. Up to 4 people per org: 1 To + up to 3 Cc. A ceiling, not a target.
2. Preference: named people with personal addresses → one named person → generic inbox greeted with a named person → generic inbox with nobody named ("Hi <Org> team") → hold.
3. Search the org's full staff roster AND run the H7 lookup for the relevant named people before dropping a level (CAPA 2026-08-18). A general inbox may be the To only after H7 found nobody usable. (Chris 2026-11-02)
4. A generic inbox may be the To only after the staff page was found and read (CAPA 2026-10-30).
5. Choose people by role, not title keyword.
6. Events (OM-2): call-for-speakers contact first, then the contact named on the event page, then the director of the department that owns the event.
7. Greeting names every named person, by the first name they GO BY as printed on the org's own page — the people step records it from the page; titles ("Rev.", "Dr.", "Very Rev.") are never names. A person named only on another org's page, or found only in Apollo, is never greeted unless they are a recipient. Never assume a pronoun. (Chris 2026-11-10, Issue 4 — the old Machine 1 rule U2, names as printed on the source page)
8. Recipients are fixed at Email 1; Emails 2 and 3 go to whoever Email 1 actually went to, including Chris's hand edits — except a successor added under J6 (Chris 2026-10-30).
9. When the org's own pages name nobody at all, a free Apollo people search on the org's own domain finds up to 5 people by role; they then go through the H7 lookup like any named person, and only an address H7 promotes is ever used (Chris 2026-11-10, Issue 1).

## H · Verification
1. An address counts only if (a) it is printed on the org's own live webpage, or (b) it belongs to a person named on the org's own live webpage and passes H7. Zero guessed addresses (CAPA 2026-08-11). (Chris 2026-11-02, CAPA 2026-11-02 apollo-roster-sweep)
2. Apollo confirms the person is real and still there.
3. ZeroBounce checks the address.
4. A PRINTED address (own page or own auto-reply) is used whatever Apollo and ZeroBounce say — their results are recorded and an "invalid" is flagged, never a hold (Chris 2026-11-09). An Apollo-found address (H7) that ZeroBounce calls invalid is skipped and the search continues with the org's other people. Catch-all and unknown proceed, flagged.
5. Follow-ups are not re-checked; delivery already proved the address.
6. An address given in the org's own auto-reply counts as provenance (it comes from the org's own mail system); it still gets the ZeroBounce check (H3) and hold-only-on-invalid (H4). (Chris 2026-10-30)
7. Apollo lookup for named people without a published address (Chris 2026-11-02). Look up at most 5 people per org, chosen only by how relevant their role or title is to the owning machine's pitch; never pad to 5. An address Apollo returns is a CANDIDATE until all three hold: Apollo email status Verified · ZeroBounce valid (catch-all allowed, flagged ⚠) · the address is on the org's own domain. An Extrapolated or otherwise unverified address stays a candidate and is never used. Candidates are never written to the master list, a draft, a dossier or a send list. Every lookup is recorded with its result and credits (resolved / held / queried-null) so a person is not paid for twice.
8. An inbox counts as the org's OWN (ENG-R008 keeps vendor and event-management inboxes out) when it is on the org's domain, on the parent of the org's own sub-site (aimh.gsu.edu → gsu.edu), or a free-mail inbox (gmail…) printed on the org's own page — volunteer-run associations use one. A vendor company's inbox is none of these (Chris 2026-11-10, Issue 1).

## I · The sequence
1. Email 1: a Gmail draft with the machine's attachment; Chris sends it by hand.
2. Email 2: 7 days after Email 1 actually went out. Email 3: 7 days after Email 2, with the starter kit attached.
3. Emails 2 and 3 go out at 7:00 AM Eastern on business days only. One that falls on a non-business day is DELAYED to 7:00 AM Eastern on the next business day, never skipped. The next email is timed from the day the previous one actually went out.
4. Overdue on restart: send the next email at the next 7:00 AM slot and continue the sequence from there.
5. Stop the sequence when: any person on the thread writes back · the thread carries ★ ✗ ⚠ or ⏸ · a draft is open on the thread · the To bounced. A bounced Cc is dropped from the next email.
6. Close: 7 days after Email 3 with no reply → ✗.
7. Review hold: a thread flagged review-hold gets its next email drafted as a reply on its existing thread instead of sent. Chris reviews and sends it; Gmail then shows the send and the thread rejoins the automated routine, timed from his send date. (Chris 2026-10-30)
8. The org's name in the subject (Chris 2026-11-10, Issue 4 — the old Machine 1 rule ratified 2026-08-12/14, restored at its root): the short name the org prints about ITSELF (logo, masthead, footer, about text), recorded by the helper that reads its own site and checked against its web address. Never an invented acronym, never a place or event name in brackets ("Texas", "Boca"). A printed short name the web address does not back is used and flagged on the dossier card; with no short name, a plain shortening of the org's own formal name, flagged.

## J · Out-of-office
1. An auto-reply is never a reply.
2. One person out never delays the thread: send on schedule to everyone.
3. Delay only when every recipient is out: send the day after the earliest return date (next business day, 7 AM Eastern).
4. Email 3 also waits while an auto-reply is still active.
5. Never email the covering colleague.
6. Successors (Chris 2026-10-30): when an auto-reply says a recipient has left or handed over their role and names a successor, the successor takes that recipient's spot (To stays To, Cc stays Cc). If several successors are named, use the one whose title or stated responsibility best matches our request — auto-replies often say who handles which kind of request; follow that routing. If several are named with no information to choose between them, Cc both. The 4-person ceiling (G1) still holds: if adding both would exceed it, add the most relevant one (or the first named) and flag ⚠ in the report. A successor at a different organization is a different org: never added to this thread if that org already has its own thread or an exclusion (C2) — flagged ⚠ instead. A colleague covering a temporary absence is not a successor (J5 still applies).
7. Never mention the absence.
8. Conferences named in auto-replies feed discovery as leads.

## K · Replies
1. Test: is the ball in Chris's court? Yes → ★ (Chris writes the reply). No (soft no, keep on file, forward without commitment) → ✗, final and immediate. Unclear → ★ + ⚠.
2. A ✗ reply that names a condition for coming back is saved word for word.
3. A reply naming a decision month or a closed speaker lineup updates the event's timing for next year.
4. Meetings are detected from Gmail invites, Fathom and agreed times, and shown in the report.

## M · Running
1. Two scheduled tasks (Chris 2026-10-31, for safety). (a) THE NIGHT RUN, Sunday–Thursday, starting about 9 PM MT: read inbox → label thread state → write tomorrow's APPROVED SEND LIST → review-hold replies as drafts → LOOP {discover → qualify and route → find and verify people → draft Email 1}, pass after pass, working only the machines still under their nightly minimum → report. The night run NEVER sends email (Gmail drafts only). It is untimed: it runs until each machine's minimum is met or its supply is exhausted (nothing left, or a full pass adds no drafts, no new people-ready orgs and no newly qualified orgs for it); a pass ceiling (25) is a last-resort guard, reported if hit. Every step and pass is timed and counted in the report. (b) THE 7 AM SEND TASK, Monday–Friday ~06:52 ET, the only task allowed to send: it sends Emails 2 and 3 at 07:00 ET for exactly the rows on that morning's approved send list, and nothing else. "Approved" = passed the night run's rulebook checks; anything flagged (⚠ attention, ⏸ hold, review hold, doubtful fit, an open ruling, a successor needing Chris, a non-SEND action) is NOT approved and waits for Chris. A list is final once written and never changed. The send task re-reads each thread just before sending and skips it if anything arrived after the list was made. Email 1 is never on the list (Chris sends it by hand).
2. Progress is saved after every step; a crashed run resumes where it stopped.
3. A lock prevents two runs overlapping.
4. On the night before a non-business day, discovery and drafting still run; the send list is written for the next business day, so the sends are delayed, never skipped.
5. One morning report covers every machine.
6. Runs on Chris's MacBook (awake, Claude desktop app open, ~9 PM–5 AM MT Sun–Thu). Storage location is one setting (master/settings.json) so it can move to GitHub or Supabase later (Chris 2026-10-30). *(2026-11-03: that one setting is now the ROOT line of `_shared/orchestrator/paths.py`, the one file every program reads for where things live; the settings file is `_shared/master/settings.json`.)*

6. Email 1 drafting (Stage 7, 2026-10-31): code fills the owning machine's approved template verbatim (only the greeting and the org's short name vary, C6); Zapier creates the draft with the machine's PDF attached and labels it <machine>/0 at creation; Gate 7 reads the raw draft back (attachment bytes, unwrapped links, HubSpot Bcc, recipients, subject) before the draft counts. Gmail is searched for the org and every recipient domain immediately before each draft (C2/C4). Nightly minimums are floors to aim for; a shortfall is reported with its reason, never met by lowering a gate. Nightly ceiling: OM-1 15, OM-2 50 (Claude default 2026-10-31 — Chris to confirm). Every per-machine number (minimum, ceiling, subject, template, attachment, labels, bounces, aliases) lives in the `machines` block of the one settings file (2026-11-03).
7. Data rulings applied 2026-10-31 (Chris): "raiseyourstar.org portal orgs" is not an organization (excluded); ccaofpa.org is an alias of centerforcommunityaction.org; a conference page that lists keynote speakers counts as "keynote listed" (section F4; NAIS).
8. The night run (Stage 8, 2026-10-31; split 2026-10-31): one start, one lock for the whole night; each step runs inside it. No step deadlines (Chris 2026-10-31). It never waits for 07:00 ET and never schedules anything. A second start yields while the night run shows signs of life; a run silent for 2 hours is treated as crashed and the next start resumes it at the first unfinished step. The 7 AM send task uses its own lock file (_shared/orchestrator/.outreach-send-lock), so a long night never blocks the morning send, and the night never sends.

9. THE SUPPLY RUN (Chris 2026-11-08). A third scheduled task, every day of the week at about 1 AM MT, whose one job is to stock the shelf for the night run: discover → qualify → event-certainty check (F7, once Chris rules on its triggers) → find and verify people → rebuild → measure the shelf. It NEVER drafts, never reads or writes Gmail, never sends and never writes a send list. It runs under the same lock as the night run (holder supply-run), so the two take turns and never overlap: a supply run yields to a live night run and a night run yields to a live supply run. Unlike the night run it is timed: a hard stop at 4:30 AM MT (so it has released everything before the 7 AM ET send task); started by hand in the daytime its hard stop is 7:30 PM MT; a start after that is refused. Steps the clock cuts off are skipped and reported, never rushed. Its own session carries its own 200-web-search platform budget, which is the main reason it is a separate task. Its caps live in the `supply` block of the one settings file. The night run's loop now runs people → draft FIRST, then discover → qualify only for a machine still under its minimum (Chris 2026-11-08), and the morning report shows the shelf the supply run left and what the night found at its start, so a shortfall reads as a supply problem or a drafting problem.
10. THE DOSSIER (Chris 2026-11-10). It shows two things only: a card for each Email 1 draft going out that day, and beneath the cards the top 10 decisions or issues — never more than 10 and never a full list. The decisions are, in order: anything flagged on today's drafts, then, one of each kind in turn, doubtful-fit orgs (E2), "is this a conference?" orgs (E3) and orgs that fit neither machine (E3). The rest are only counted; they come up as the first ones are answered. Chris answers in chat by number; a yes is recorded as his ruling and the org is drafted the next night.
